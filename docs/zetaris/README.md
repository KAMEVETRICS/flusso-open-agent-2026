# Flusso on Zetaris

This document follows the Zetaris evaluation criteria: (1) build a USL (use case and sources, onboarding and exploratory queries, the USL with its DDL, proof that it is active, and a data-quality rule), and (2) reflect on it (time saved, where it helps, how to make it stronger). Real query results are in [exploration.md](exploration.md), generated by `npm run zetaris:explore`.

## 1a. Use case and data sources

**Use case.** Before Flusso writes a campaign, its evidence agent has to answer: *what happened the last times we wrote for this brand, what does the audience engage with right now, and which facts can we safely build on?* Those answers live in three different places. Zetaris federates them into one SQL surface the agent queries as a tool, and every row it returns becomes a citable evidence ID.

| # | Source | What it holds | How Zetaris reaches it | Licence / terms |
|---|---|---|---|---|
| 1 | **Flusso campaign store** (Neon Postgres) | 18 past campaigns, 348 governed claims with verification outcomes, 972 captured source sections, content performance | JDBC datasource `flusso_neon` plus 4 datasource views that unpack the jsonb campaign packs at the source | Flusso's own data |
| 2 | **Hacker News search API** (hn.algolia.com) | Stories that link to a brand's domain: points and comment counts | Lightning REST tables in `flusso_signals` for the demo brands; per-run REST session tables for any other brand | Public API, no key |
| 3 | **Wikimedia pageviews API** | Monthly English Wikipedia article views for the brand | REST session tables (article lookup, then pageviews), created and dropped by the agent | Public API, CC0 data, User-Agent required |

## 1b. Onboarding and exploratory queries

All objects are created by [scripts/zetaris-setup.mjs](../../scripts/zetaris-setup.mjs) from the definitions in [lib/agent/zetaris-catalog.ts](../../lib/agent/zetaris-catalog.ts). The default is a dry run that prints every statement with credentials masked; `--apply` runs them and logs each one (masked) to `logs/audit.jsonl`.

```bash
npm run zetaris:setup              # dry run
npm run zetaris:setup -- --apply   # create the objects
npm run zetaris:explore            # run the exploratory queries, write exploration.md
```

The setup creates, in order: the `flusso_neon` JDBC datasource; datasource views `fl_campaign_history`, `fl_claim_outcomes`, `fl_performance`, and `fl_evidence_sections` (native Postgres SQL, so jsonb is unpacked in Neon and only flat rows cross the wire); the `lightning.metastore` and `lightning.metastore.flusso` namespaces; the `brand_evidence` USL; one ACTIVATE per USL table; two DQ rules; and the `flusso_signals` Lightning database with three Hacker News REST tables.

[exploration.md](exploration.md) holds 2 to 4 exploratory queries per source with their real output: campaigns per domain, claim outcomes across brands, sections per brand (source 1); top stories, engagement per brand, stories per year (source 2); monthly views, and peak versus average month (source 3).

## 1c. The USL, proof that it is active, and data quality

**DDL** (as sent by the setup script):

```sql
COMPILE USL brand_evidence DEPLOY NAMESPACE lightning.metastore.flusso DDL
CREATE TABLE campaign (
  campaign_id varchar(80) NOT NULL PRIMARY KEY,
  brand varchar(200),
  domain varchar(200),
  goal varchar(1000),
  editorial_score int,
  fact_count int,
  gap_count int,
  claim_count int,
  platforms varchar(400),
  created_at timestamp
);
CREATE TABLE claim_outcome (
  campaign_id varchar(80) FOREIGN KEY REFERENCES campaign(campaign_id),
  domain varchar(200),
  claim_id varchar(80),
  claim_kind varchar(40),
  status varchar(40),
  resolution_status varchar(40),
  repair_action varchar(60),
  claim_text varchar(400),
  recommendation varchar(400),
  source_id varchar(200),
  created_at timestamp
);
CREATE TABLE performance (
  performance_id varchar(120) NOT NULL PRIMARY KEY,
  campaign_id varchar(80) FOREIGN KEY REFERENCES campaign(campaign_id),
  domain varchar(200),
  platform varchar(40),
  asset_type varchar(60),
  hook_id varchar(80),
  territory varchar(200),
  impressions bigint,
  engagements bigint,
  clicks bigint,
  conversions bigint,
  updated_at timestamp
);
CREATE TABLE evidence_section (
  evidence_id varchar(300) NOT NULL PRIMARY KEY,
  campaign_id varchar(80) FOREIGN KEY REFERENCES campaign(campaign_id),
  domain varchar(200),
  section_id varchar(200),
  source_id varchar(200),
  heading varchar(400),
  excerpt varchar(600),
  created_at timestamp
)
```

Each table is activated from its datasource view, for example:

```sql
ACTIVATE USL TABLE lightning.metastore.flusso.brand_evidence.campaign AS
SELECT COALESCE(campaign_id, '') AS campaign_id, brand, domain, goal, editorial_score, fact_count,
       gap_count, claim_count, platforms, created_at
FROM flusso_neon.fl_campaign_history
```

**USL active.** [exploration.md](exploration.md) shows `SHOW NAMESPACES OR TABLES` with every table activated, a claim-failure-rate query joining `claim_outcome` to `campaign` on the declared key, an evidence-reuse query joining `campaign` to `evidence_section`, and `LIST DQ USL`.

**Data-quality rules.**

```sql
REGISTER DQ claim_status_known TABLE lightning.metastore.flusso.brand_evidence.claim_outcome AS
  status IN ('supported', 'unsupported', 'conflict', 'time-sensitive', 'editorial') AND claim_text IS NOT NULL
REGISTER DQ campaign_has_domain TABLE lightning.metastore.flusso.brand_evidence.campaign AS
  domain IS NOT NULL AND domain <> ''
```

The agent runs both with `RUN DQ` at the start of every run and records the result in its plan. On the live data, `claim_status_known` passes 348 of 348 rows, and `campaign_has_domain` fails 3 of 18: early test campaigns created without a website. Because every agent query filters on the domain, those rows cannot leak into a brand's evidence; the DQ result makes that exclusion visible instead of silent.

## How the agent uses Zetaris

The agent never writes SQL. It picks from eight parameterised tools ([lib/agent/evidence-tools.ts](../../lib/agent/evidence-tools.ts)), and the domain and search terms are bound as escaped literals:

| Tool | Zetaris object |
|---|---|
| campaign_history | `brand_evidence.campaign` |
| claim_risk | `brand_evidence.claim_outcome` joined to `brand_evidence.campaign` |
| claim_risk_baseline | `brand_evidence.claim_outcome` across all brands |
| unsupported_claims | `brand_evidence.claim_outcome` |
| performance | `brand_evidence.performance` |
| prior_evidence | `brand_evidence.evidence_section` |
| audience_signals | REST session table over the Hacker News API |
| attention_trend | two REST session tables over Wikipedia search and Wikimedia pageviews |

Each returned row gets an ID such as `claim_risk#2`. A decision has to cite those IDs, and the code verifier rejects any that cite a row the agent never received. Every query is logged with its Zetaris query ID, SQL, row count, and timings to `logs/trace.jsonl` and `logs/telemetry.jsonl`, and each accepted decision's chain back to the query IDs is in `logs/provenance.jsonl`.

## 2a. Did the USL save time compared with a hand-coded approach?

Yes, mostly in two places.

**The hand-coded alternative.** Without Zetaris, the claim-risk tool has to open a Postgres connection from the app, unpack jsonb in a query the app owns, and join it by hand:

```ts
// Hand-coded claim_risk: the app owns the connection, the jsonb shape, and the join.
const rows = await sql`
  SELECT COALESCE(c->>'claimKind', 'unclassified') AS claim_kind, c->>'status' AS status, count(*) AS claims
  FROM campaign_runs r CROSS JOIN LATERAL jsonb_array_elements(COALESCE(r.delivery_pack->'proofReport'->'claims', '[]'::jsonb)) c
  WHERE lower(substring(COALESCE(r.brief->>'website', '') from '^[A-Za-z]+://(?:www[.])?([^/:?#]+)')) = ${domain}
  GROUP BY 1, 2 ORDER BY claims DESC`;
// ...then fetch() Hacker News and Wikimedia, flatten their JSON in TypeScript, type each field,
// add retries, and write a separate data-quality check for each table.
```

The jsonb unpacking and domain normalisation would be repeated in every tool, and the two REST sources would each need their own client, flattening, and typing. With the USL, those rules live once in the view and USL definitions (about 110 lines in `zetaris-catalog.ts`), and each tool is a one-line `SELECT` on a named table. Adding a REST source is one `CREATE REST SESSION TABLE` statement plus a `LATERAL VIEW explode` query, not a new HTTP client.

**Where it saved the most.** The data-quality rules. Writing `campaign_has_domain` took one statement and found the 3 bad campaigns on its first run. A hand-coded check would have needed its own query, its own reporting, and a decision about where to call it.

**Where it cost time.** Learning the activation rules: `ACTIVATE` refuses a nullable expression for a `NOT NULL` key (fixed with `COALESCE`), a fresh instance needs `lightning.metastore` created before the namespace, and `DESCRIBE BY` accepts only a restricted character set. Each took one failed statement to find, and the error messages said exactly what to change. Queries also take 4 to 12 seconds through the federation layer, against well under a second directly on Neon; the agent runs up to three tools in parallel to absorb that.

## 2b. Where the USL helps, and where it does not

It helps when the agent needs **one vocabulary across sources**. `domain` means the same thing in all four USL tables, and the keys let a join from claims to campaigns be written without knowing how the jsonb is shaped. It also helps with **auditability**: a judge can rerun any query the agent ran, by its logged SQL, in the Zetaris UI.

It helps less for **per-request REST data**. The USL cannot be activated from a REST endpoint whose URL depends on the brand, so the live signals bypass the USL and go through session tables: three statements per signal, and the agent manages their lifecycle. Persistent REST tables have a second problem we hit: their schema is inferred once, at creation. The `hn_wise_com` table now fails every query with a Spark `StructConverter` index error, because later API responses no longer match the inferred struct; the same API through a fresh session table works. A `UNION ALL` across REST tables with different inferred schemas fails the same way. It also does not cover **text search**: `prior_evidence` uses `LIKE` over excerpts, while Neon already has a full-text index on the same sections that the federated query cannot use.

A project that would benefit more: an agency running campaigns for 30 brands, each with its own analytics export, CRM, and ad-platform data. A USL over those with shared `domain` and `campaign_id` keys would replace 30 sets of per-brand connectors. We estimate the saving at roughly one day of integration work per new brand, since adding a brand becomes registering its sources and activating the same USL tables.

## 2c. How to make the USL stronger: a requirement

**Requirement: parameterised REST activation for USL tables.**

*Problem.* Agents query live APIs whose URLs depend on the entity being asked about (a brand domain, a ticker, a city). Today a USL table can only be activated from a fixed query, so an agent must create, read, and drop a session table per request, and that data never gets USL keys or DQ rules.

*Requirement.* Let `ACTIVATE USL TABLE` bind to a REST endpoint template whose placeholders come from equality predicates in the query, with a cache TTL per binding.

*Acceptance criteria.*
1. `SELECT ... FROM <usl>.audience_signal WHERE domain = 'linear.app'` calls the endpoint with `{domain}` filled in and returns rows typed by the USL DDL.
2. A query without a value for a required placeholder fails with an error that names the missing placeholder.
3. DQ rules run on the bound rows like any other table.
4. Responses are cached per binding for the declared TTL, and `SHOW DQ` reports the cache age.
5. The query log records the resolved URL.

*Mock of the result:*

```sql
-- Proposed syntax, not supported today.
COMPILE USL brand_evidence DEPLOY NAMESPACE lightning.metastore.flusso DDL
CREATE TABLE audience_signal (
  domain varchar(200) NOT NULL,
  title varchar(400),
  points int,
  num_comments int,
  created date
);

ACTIVATE USL TABLE lightning.metastore.flusso.brand_evidence.audience_signal AS REST TEMPLATE (
  endpoint "https://hn.algolia.com/api/v1/search?query={domain}&tags=story&hitsPerPage=50",
  method "GET", response_type "JSON", cache_ttl "1h"
) SELECT '{domain}' AS domain, h.title, h.points, h.num_comments, to_date(h.created_at) AS created
  FROM response LATERAL VIEW explode(hits) AS h;

-- The agent's tool becomes one query, joinable with the rest of the USL:
SELECT s.title, s.points, c.goal
FROM lightning.metastore.flusso.brand_evidence.audience_signal s
JOIN lightning.metastore.flusso.brand_evidence.campaign c ON c.domain = s.domain
WHERE s.domain = 'linear.app'
ORDER BY s.points DESC LIMIT 10;
```

With this in place, Flusso's `audience_signals` and `attention_trend` tools shrink from four to six statements each to one query, and their rows gain the same keys and DQ coverage as the campaign store.
